## 1. 结论摘要

`192.0.2.5` 的导航容器**不是**照搬 G1 的配置，而是一份**手工对齐过的 G1 配置**：G1 专项项（`robot_model`、机体几何、雷达外参）都已正确设置，能跑起完整的雷达 + SLAM/规划链路。

但存在 1 个 **P0 级缺陷**和 3 个 P1/P2 级差异：

| 级别 | 问题 | 后果 |
|---|---|---|
| **P0** | livox 驱动未打 IMU extrinsic 补丁，`/livox/imu` 重力为 **−1g** | 点云已翻正、IMU 没翻 → 两者矛盾 → **SLAM 建图上下颠倒**（即 G1 文档 §9.2 记录过的同一个 bug） |
| P1 | 本机**没有 G1 桥接容器**，无 `/cmd_vel` 订阅者、无 `/sdk/imu` | 导航能算路径，但**机器人收不到速度指令**，闭环不通 |
| P2 | `g1_start.sh` 硬编码 `enp4s0`，本机机器人网卡是 `enp132s0` | 将来部署桥接容器时会报 `does not match an available interface` |
| P2 | 两机时钟曾相差约 22 天（详见 §4.5，初版归因已更正） | bag / 日志时间可能无法与其他机器对齐 |

## 4. 关键发现

### 4.1 【P0】IMU 倒装修复补丁缺失

**这是本次核查最重要的发现。** G1 头部 MID360 是倒装的（官方 URDF `mid360_joint` 的 rpy roll=180°），原版 `livox_ros_driver2` 只把 `extrinsic_parameter` 应用到点云、不应用到 IMU，导致点云朝向与 IMU 重力方向矛盾，SLAM 建图上下颠倒。G1 侧已于 2026-08-31 修复（文档 §9.2）。

在 `192.0.2.5` 上，该修复**只做了一半**：

- 配置文件里 `roll: 180` ✅ → 点云被翻正
- 驱动源码 `pub_handler` **未打补丁** ❌ → IMU 没有被翻

**两条独立证据：**

**(1) 静态 —— 源码 md5 比对**

| 文件 | G1（已打补丁） | 192.0.2.5 | 一致的补丁内容 |
|---|---|---|---|
| `src/comm/pub_handler.h` | `0c6a9b3fbd61015e1efe466a15b1cebc` | `39836a4bf56f659406c5007bc7460f4f` | 不同 |
| `src/comm/pub_handler.cpp` | `5f778e7fc4be3294ec9bf5ead0af7e0d` | `6e8b5c7d179df1bda1312727614a9e01` | 不同 |

**(2) 运行时 —— G1 文档规定的判据**

```
$ rostopic echo /livox/imu -n 2 | grep -A4 linear_acceleration
linear_acceleration:
  x: -0.03258124
  y:  0.00848469
  z: -1.00570440      # ← 判据：倒装未纠正 ≈ −1.0；翻正后应 ≈ +1.0
```

**补丁差异已逐行确认，可直接套用。** 把远端驱动源码拉回与仓库补丁版 `diff` 后，真实差异**只有 3 处**（其余为拼接产生的许可证头偏移）：

1. `SetLidarsExtParam` 返回类型 `void` → `ExtParameterDetailed`；
2. 新增静态成员 `static ExtParameterDetailed extrinsic_;` 及其定义；
3. IMU 回调中把 `extrinsic_.rotation` 乘到 gyro 与 acc 上（原本是直通赋值）。

结论：**无版本漂移，补丁是干净的可直接覆盖**。

### 4.2 【P1】机器人控制链路完全缺失

本机只有导航栈，没有任何 G1 控制侧组件：`docker ps -a` 中无 `g1-bridge`，`/home/operator/g1bridge` 不存在，`/cmd_vel` 无订阅者，`/sdk/imu` 不存在。

意味着当前状态是**"能算不能走"**：SLAM / 规划 / Web 都正常，但速度指令没有出口。要形成闭环，必须补一个桥接容器。

### 4.3 【P2】`networkInterface` 指向无线网卡

`x_nav.yaml` 中 `robot.networkInterface: wlp131s0f0`（`192.0.2.5`，办公无线网），而非机器人网段的 `enp132s0`（`192.0.2.6`）。

**当前无害**：`robot_model: G1_BRIDGE` 不命中 `robot_web_controller.py` 的任何分支，导航容器内不起机器人控制节点，该字段无人读取。**但它是未来部署桥接容器的定时炸弹**——见 §5.2。

### 4.4 配置生效机制：两台机器不同（值得留意）

| | G1 基准 | 192.0.2.5 |
|---|---|---|
| 机制 | `robot_web_controller.py` 启动驱动时显式传 `_user_config_path:=/nav_map/MID360_config.json` | 依赖 `x_nav.yaml` 顶层 `user_config_path` 被 `rosparam load` 到**全局参数** `/user_config_path`，驱动以相对参数名解析后命中 |
| 验证 | 文档 §9 记录 | 已实测：`rosparam get /user_config_path` → `/nav_map/MID360s_config.json`；驱动进程 fd 指向该文件 |

`192.0.2.5` 上驱动进程**命令行无任何参数**（`/proc/818/cmdline` 仅二进制路径），`/livox_lidar_publisher/user_config_path` 也未设置，但 `/proc/818/fd/10 → /nav_map/MID360s_config.json`——证明配置确实通过全局参数生效。

> ⚠️ 值得注意：G1 主机上同样的顶层 `user_config_path` 键（连 8月28日的 `.g1bak` 备份里都有）**当时并未让驱动生效**，才需要额外打 `robot_web_controller.py` 的显式参数补丁。两台机器走了不同路径却都成功了，说明"全局参数"这条路径对驱动构建版本敏感。**建议在 192.0.2.5 上也补上显式参数**（见 §5.3），消除这个不确定性。

### 4.5 【P2】其他

- **主机时钟（本项已更正）**：核查过程中两台机器的时间**发生过变化**。

  | 时刻 | navigation-host | 192.0.2.5 |
  |---|---|---|
  | 核查初期 | 2026-09-16 10:57 CST | 2026-10-08 14:47 CST |
  | 核查末期 | 2026-10-09 08:44 CST | 2026-10-09 08:44 CST |

  初版报告据初期读数判定"192.0.2.5 快约 22 天"，**该归因是错的**：末期两机已一致，说明当时**滞后的是 navigation-host 侧时钟**，而非 192.0.2.5 超前。两侧读数在各自时刻内部均自洽（容器 `Up` 时长与 `StartedAt` 相符），故这是一次真实发生的时钟校正，不是记录笔误。

  对核查结论的影响：**无**。本报告所有判定均基于配置内容与实时数据（md5、fd、话题频率、IMU 读数），不依赖跨机时间对齐。但仍建议两机统一启用 NTP，避免 bag / 日志时间轴不可比。
- **`/nav_map` 内容冗余**：同时存在 `x_nav.yaml`、`x_nav_a2.yaml`、`a2_jt128.yaml`、`g1-ref-x_nav.yaml` 及 6 个时间戳备份，另有一个 `.test` 文件（10月8日修改）。`g1-ref-x_nav.yaml`（9月21日）是一份与 G1 基线**逐字一致**的参考配置（含相同中文注释），但当前生效的 `x_nav.yaml` 已在两处偏离它：`networkInterface` 与 `user_config_path`。

## 5. 修复建议

> 以下命令均**未执行**，需要现场确认无建图/导航任务在跑后手动执行。

### 5.1 【P0】补 IMU 翻转补丁

```bash
cd /home/operator/g1-robot

# 1) 备份原文件
docker exec nav_robot bash -lc \
  'cd /catkin_ws/src/livox_ros_driver2/src/comm && cp pub_handler.h pub_handler.h.orig && cp pub_handler.cpp pub_handler.cpp.orig'

# 2) 覆盖为已验证的补丁版
docker cp nav/livox_patch/pub_handler.h   nav_robot:/catkin_ws/src/livox_ros_driver2/src/comm/
docker cp nav/livox_patch/pub_handler.cpp nav_robot:/catkin_ws/src/livox_ros_driver2/src/comm/

# 3) 重新编译
docker exec nav_robot bash -lc \
  'source /opt/ros/noetic/setup.bash && cd /catkin_ws && catkin_make --pkg livox_ros_driver2'

# 4) 重启驱动（守护进程约 1 秒内自动拉起）
docker exec nav_robot bash -lc 'kill $(pgrep -f livox_ros_driver2_node)'
```

**验收判据**：`/livox/imu` 的 `linear_acceleration.z` 从 **−1.0 变为 +1.0**：

```bash
docker exec nav_robot bash -lc 'source /opt/ros/noetic/setup.bash; \
  export ROS_MASTER_URI=http://192.0.2.6:11311; \
  timeout 6 rostopic echo /livox/imu -n1 | grep -A4 linear_acc'
```

> 注意：备份目录不要放进 `/catkin_ws/src/` 下的包目录，否则 catkin 会因 `package.xml` 重名报冲突。

### 5.2 【P1】补桥接容器（形成闭环）

先在 192.0.2.5 上部署 `g1-bridge`。**必须改一处**：`g1_start.sh` 中硬编码的网卡名

```diff
- exec rosrun g1_ros1_sdk g1_ros1_sdk _networkInterface:=enp4s0
+ exec rosrun g1_ros1_sdk g1_ros1_sdk _networkInterface:=enp132s0
```

⚠️ 桥接容器启动**必然触发 `StandUp → 3s → Start`**，真人形会自己站起来，必须清场并有人监护。

构建所需的 `unitree_sdk2` 预编译库可用仓库脚本从导航容器提取：

```bash
cd /home/operator/g1-robot/bridge && ./fetch_unitree_sdk2.sh nav_robot
```
